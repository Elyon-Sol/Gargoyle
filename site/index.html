Receipts and holds for agent tool calls

When an AI assistant acts on your behalf,
prove exactly what was allowed, who released it,
and what ran.

Gargoyle sits between an assistant and the tools it uses. Every call gets a signed, single-use receipt bound to its arguments and to a policy version. Calls that matter stop until a named person signs a release with a key no server holds. What ran is signed too, with the state it found and the state it left. The chain verifies offline, by anyone: receipt, grant and execution in Python or TypeScript, the evidence log and witness in Python.

Who it is for

The person who has to answer for what the assistant did

Gargoyle was built for the author's own client base: small and mid-sized organizations on Microsoft Entra ID and Microsoft 365 whose staff run Claude Desktop or Claude Code, or any other client of the Model Context Protocol, against files and office records. The user is whoever is accountable when that goes wrong.

IT leads and managed service providers

You enabled the assistant on staff workstations and you will be asked what it changed, who allowed it, and whether the undo was real. Gargoyle gives that answer as a signed chain you can hand over, not a dashboard you have to be trusted on.

Owners of a compliance obligation

You need a record of every consequential action by an automated agent, with a named human release for the ones that matter, that an outside party can verify after the fact without your systems. The evidence log and the witness are that record.

One developer, one machine

You run an assistant against your own files and want writes to pause for your click, with an exact undo. The local mode needs one process and a rules file, and no identity provider.

It is not for you if you need a gateway with discovery filtering, masking and dashboards, or if you need to prevent a workstation's own administrator from acting around the gate. Gargoyle is a narrow gate that detects that; it does not pretend to prevent it.

What it proves

One sentence, every clause signed by a different key

A specific policy version authorized a specific call for a specific person; named approvers released it in the state they were shown; exactly that call ran once; here is what it changed; and if it was undone, the undo was exact. Nothing in the chain asserts what its hashes cannot prove.

1The receipt

Issued by a policy decision, signed by the issuer, bound to the tool, the hash of its arguments, the caller, and the policy version. Single use. It stops being honored the moment the policy it was decided under changes.

2The grant

A human's release, signed with a key generated in their browser and never exported. Verified at execution, not in a dashboard. Thresholds and named approvers live inside the receipt's signature, so a client cannot lower them.

3The execution receipt

The executor's signed statement that this receipt's call ran, with the hash of its outputs and the target's state before and after. A write runs only if the target is still as the approver saw it.

4The evidence log

One hash-chained entry per decision, refusals included, naming the person, the client and the target. Verifiable offline across every format version the project has had.

5The witness

The issuer's own signed record of every decision, kept on a server the workstation does not control. Reconciled against the evidence by decision id, it names a forged entry, a bypassed approval or a suppressed record.

6The audit

One command verifies the chain, reconciles it with the witness, and checks the gated folder for any file changed around the gate. It has refused to label a revert that was not byte-exact, and it caught a defect in its own author's code.

How it works

A small middleware in front of the tools the assistant already has

The gate speaks the Model Context Protocol. It runs beside the client as a local process, or as an HTTPS server for hosted connectors, and fronts whatever tool server the assistant uses: a filesystem, a Microsoft 365 server, anything that speaks the protocol. The assistant is told, in the protocol handshake, that all work on the target goes through the gate; nobody types a server name.

Free calls

Reads and listings get a receipt and run at once. The user notices nothing.

Held calls

A write pauses. The approver's console shows the exact change as a diff against the file as it is, or an inbox rule in plain words with outside addresses called out. One click signs the grant.

Refused calls

A delete the policy forbids, a key the executor does not trust, a file that moved under the card: each is refused, and each refusal is evidence.

Plans and undo

A long task can ask for one approval covering a bounded plan, each step still bound and single-use. An approved change can be undone through the same approval, and the audit proves the undo was exact.

41 ok honored write_file <workstation account> CHAIN_VERIFIED released by <approver> (plan c04e683b step 1) state 0c8a2f3d -> 97b2f1cc via claude-ai 0.1.0 42 ok honored write_file <workstation account> CHAIN_VERIFIED released by <approver> (plan c04e683b step 2) state f68e4696 -> 5746e13f via claude-ai 0.1.0
Two rows from a live audit: a named person's assistant, identified as Claude Desktop, made two changes under one plan a named approver signed, each bound to the file state it found, each transition recorded, every signature verified on the workstation.
Evidence, not promises

Proven on real machines, with real identities

A Windows 11 workstation running Claude Desktop, an issuer on a separate host over TLS, Microsoft Entra ID identities for the person asking and the person approving, and 45 verified audit rows: free reads, held writes, three kinds of refusal, a state-bound write, an exact revert and one the audit would not call a revert, a scoped plan, a reconciliation against the issuer's witness, and a hand edit in Notepad caught by the tree check.

  • The audit withheld the "reverts" label from a revert whose bytes differed, which exposed a newline bug in the project's own filesystem server. The next revert was exact.
  • A full work task cost two approval cards and about twenty seconds; everything else ran unnoticed. Where friction appears, the policy file is the lever, not the mechanism.
  • On a workstation its user administers, the gate constrains the assistant, not the user. A change made around the gate is detected, not prevented, and the specification says so.
Get it

Three commands, no policy engine, no containers

# the issuer and an approver, on the server
pip install gargoyle-receipts
gargoyle init /path/the/assistant/may/touch      # keys, config, a JSON rules file
gargoyle issuer                                  # the issuing service, with the browser console at /approve

# the workstation: paste the written MCP entry into Claude Code or Claude Desktop
gargoyle login --tenant ... --client-id ... --scope ...   # optional: the user's own Entra identity
gargoyle audit --log audit.jsonl --witness witness.jsonl --check-tree /the/folder

The full single-instance build is in the repository's guide (Ubuntu on Hyper-V, Apache with TLS, a Windows 11 client). The specification is self-contained, with conformance vectors a second implementation reproduces byte for byte. The limits are written down in the report.

Where this stands. Pre-release, version 0.16. One author. One live deployment, on the author's own tenant, with forty-five verified audit rows. One outside review of the public repository has completed: a language model of the same family as the one that co-wrote the code, with repository access, ran the suites, verified the package against the tag and found the authorization and identity gaps fixed in 0.16. No human review has. The specification and the conformance vectors exist so that someone who trusts none of this can verify a chain for themselves; until someone has, every claim on this site is self-reported, and the threat model and limits are the section to read first.
