Pre-execution admission control · canon v0.9.8.4

A gate that decides whether an action is allowed
to happen — before it happens.

Elyon-Sol is a deterministic, fail-closed HTTP admission gate derived from a formal admissibility specification. Given a request and a SHA-256-pinned manifest, it returns ELIGIBLE only if the caller's authority and operation sets satisfy the manifest and the continuity property holds — otherwise it refuses, and the upstream is never called.

G(I) = AC³ ∧ T²⁶ ∧ CCS

Plainly: allow only if the caller's authorities cover what the manifest requires (AC³), the operations are covered (T²⁶), and nothing the decision relied on has changed (CCS). Per the canon, the superscripts are legacy labels — not exponents.

What it is

An authorization boundary for actions, not just requests

The gate constructs an admissibility envelope on every ELIGIBLE decision — a content-hashed record of the full decision context (canon, manifest, evaluator, request, condition results, timestamp), signed with the gate's key. The upstream target performs an action only if the request carries a valid, current, correctly-bound, single-use envelope. A decision must pass two set-containment checks on the request plus one continuity property that carries across changes — all fully implemented:

Authority AC³

The caller's authorities must include everything the manifest requires — a set-containment check, AP ⊇ AR. Canon §§11.3, 11.5.

Coverage T²⁶

The caller's operations must be covered by what the manifest permits — the same set-containment check on the operation sets, OP ⊇ R. Canon §§11.4, 11.6.

Continuity CCS

The one that actually holds over time: any change to canon, manifest, or evaluator invalidates a prior ELIGIBLE, so a stale “yes” never persists. Canon §§12–13.

Key features

What the system enforces

⛔ Fail-closed by design

On REFUSE or any exception the upstream is never called. It trades availability for safety — when it cannot be sure, it refuses.

✒️ Signed admissibility envelope

Every ELIGIBLE decision is bound into an Ed25519-signed, content-hashed record over canonical JSON — tamper-evident and verifiable target-side.

🔗 Action & body binding

A decision binds to exactly one target and one action, so a token minted for action A cannot release action B. The target checks the interaction it receives; behind Envoy, the ext-authz sidecar binds the request body only once a body-binding mapping is declared — until then it refuses forwarded requests.

1️⃣ Single-use replay defense

Each envelope is honored once. A shared-store replay cache fails closed at startup under horizontal scale without a coherent backing store.

👤 Human-oversight governance

High-impact actions return 202 PENDING_APPROVAL and are held until a separate human approver signs a grant — separation-of-duties enforced by role in the signed key record.

🛡️ Non-bypass topology

mTLS client-auth proves the gate is the only authorized caller of the target; an OPA/Envoy ext-authz sidecar answers ALLOW/DENY reusing the production verifier.

⏱️ Freshness & clock-skew

Signed published-record freshness plus a configurable clock-skew window; a stale or out-of-window record is refused rather than trusted.

🔑 Key provenance & rotation

Approver and issuer trust is resolved from a signed key-record chain, with roles kept apart: the gate's key cannot approve, and an approver's key cannot sign a token. Publisher keys are rotatable live under a no-secret-in-history protocol.

🧾 Auditable & reconcilable

An issuance/approval log lets every held-and-forwarded high-impact decision be reconciled — a forward without a recorded grant is a caught invariant violation.

vs capability-token systems — the honest comparison

The table above is against access-control styles. The sharper question is against systems that already issue signed, bound tokens — macaroons, biscuit, SPIFFE/SVID, GNAP, and the IETF Transaction Tokens draft. Stated plainly: an admissibility envelope is a capability token — signed, action-bound, single-use — and Elyon-Sol claims no new cryptographic primitive. What it adds is behavioral: the envelope is a receipt of a policy decision (it pins the exact canon, manifest, and evaluator that decided), it self-invalidates when that policy changes, it makes human approval a cryptographic separation-of-duties primitive, and it ships with a reproducible, self-hostable break-it challenge. It composes with these systems — it can run on top of a biscuit rather than instead of one.

Try it — self-host

Spin it up, then break it

The public nodes are retired, but the whole surface is open source — stand up your own instance in a couple of commands, then try to break it with nothing but curl and jq.

Preserved as documentation. The credited red-team challenge is closed; adjudicate a suspected break against your own instance with the inspector (the tool decides — deploy/INSPECT_YOUR_BREAK.md).

0 · Spin up your own gate + target + publisher
git clone https://github.com/Elyon-Sol/Elyon-Sol.git && cd Elyon-Sol
python deploy/bootstrap_config.py            # gate keypair + pinned anchor -> deploy/.env
cd deploy && docker compose up --build       # gate:8000  target:9000  publisher:9100

# in another shell, point the walkthrough at your instance:
export GATE=http://localhost:8000  TARGET=http://localhost:9000  AUTHZ=http://localhost:9200
# full guide: deploy/SPIN_UP_YOUR_OWN.md   (AUTHZ needs the docker-compose.authz.yml overlay)
1 · Make a governed call — the gate signs, forwards, and the target acts once
INTERACTION='{
  "AP": ["identity","role"],
  "OP": ["session","request"],
  "context": {
    "tool": "transfer_funds",
    "args_sha256": "ee0885070ca8ca1ff7df3e53275c4cadb3fbf747f3e0ea380a002f8c69ab8e9d"
  },
  "expected_manifest_version": "1.0",
  "expected_manifest_sha256": "ac18ac78c39dfed3d202964ab5e88d34a87ddebf8b41c1abda49bf75a0bcaeb1"
}'

# target_url is the target's IN-NETWORK identity — the compose gate only forwards to `target`
ENV=$(curl -s $GATE/governed-call \
  -H 'content-type: application/json' \
  -d "{\"target_url\":\"http://target:9000/target\",\"interaction\":$INTERACTION}" \
  | jq -c '.envelope')
2 · That governed call already acted — so re-presenting the token is a replay
# the /governed-call above admitted, signed, AND forwarded to the target, which acted once
# (GET /received went up by 1). The envelope is single-use, so presenting it again is a replay:
curl -s $TARGET/target \
  -H "X-Elyon-Sol-Envelope: $ENV" \
  -H 'content-type: application/json' \
  -d "$INTERACTION" | jq
# expect: {"detail": {"honored": false, "reason": "REF_VERIFY_REPLAY"}} — single-use working
3 · Now try to break it — every one of these SHOULD be refused
# a) no token at all
curl -s $TARGET/target -H 'content-type: application/json' -d "$INTERACTION" | jq

# b) replay the same valid token a second time
curl -s $TARGET/target -H "X-Elyon-Sol-Envelope: $ENV" -H 'content-type: application/json' -d "$INTERACTION" | jq

# c) forge — tamper one byte of the signed envelope
FORGED=$(echo "$ENV" | jq -c '.decision_sha256 = "deadbeef"')
curl -s $TARGET/target -H "X-Elyon-Sol-Envelope: $FORGED" -H 'content-type: application/json' -d "$INTERACTION" | jq

# d) rebind — reuse the token but claim a different action
REBIND=$(echo "$INTERACTION" | jq -c '.context.tool = "delete_database"')
curl -s $TARGET/target -H "X-Elyon-Sol-Envelope: $ENV" -H 'content-type: application/json' -d "$REBIND" | jq

# e) sidecar — ALLOW/DENY only; it reads the interaction from a one-line HEADER, not the body
I_HDR=$(echo "$INTERACTION" | jq -c .)
# control: a fresh, never-presented token -> ALLOW (minting it makes the target act once more)
FRESH=$(curl -s $GATE/governed-call -H 'content-type: application/json' \
  -d "{\"target_url\":\"http://target:9000/target\",\"interaction\":$INTERACTION}" | jq -c '.envelope')
curl -s -o /dev/null -D - -X POST $AUTHZ/authz -H "X-Elyon-Sol-Envelope: $FRESH" -H "X-Elyon-Sol-Interaction: $I_HDR" | grep -i '^x-elyon'
# now try for ALLOW without a valid token: forged, replayed, rebound (ALLOW = finding)
curl -s -o /dev/null -D - -X POST $AUTHZ/authz -H "X-Elyon-Sol-Envelope: $FORGED" -H "X-Elyon-Sol-Interaction: $I_HDR" | grep -i '^x-elyon'
curl -s -o /dev/null -D - -X POST $AUTHZ/authz -H "X-Elyon-Sol-Envelope: $FRESH" -H "X-Elyon-Sol-Interaction: $I_HDR" | grep -i '^x-elyon'
curl -s -o /dev/null -D - -X POST $AUTHZ/authz -H "X-Elyon-Sol-Envelope: $FRESH" -H "X-Elyon-Sol-Interaction: $(echo "$REBIND" | jq -c .)" | grep -i '^x-elyon'

Expected: a–d all refuse — REF_VERIFY_ENVELOPE_ABSENT, REF_VERIFY_REPLAY, REF_VERIFY_SIGNATURE_INVALID, REF_VERIFY_BINDING_MISMATCH; for e, the control prints ALLOW and the three attempts print DENY (REF_VERIFY_SIGNATURE_INVALID, REF_VERIFY_REPLAY, REF_VERIFY_BINDING_MISMATCH). Make any of them act, and you have found a real gap — report it per SECURITY.md.

The sharper edges. Those five are the easy cases and they refuse. A real break in a system like this lives in an implementation seam — where the gate and the target disagree about what a request means. The classes worth your time: canonicalization mismatch (reordered or duplicate JSON keys, raw vs escaped unicode, NFC vs NFD, 1 vs 1.0), a field the signature does not cover (mutate one field at a time), single-use under real concurrency (present the same token many times at once, not in sequence), validity-window edges (a token expired to one host but not another), and cross-binding (a token minted for A honored for B). Archived attack brief from the live period: deploy/BREAK_IT.md.

Red-team challenge — archived

Break Elyon-Sol — the open challenge (closed 2026-07-20)

Archived. This section records the challenge as it ran while the public nodes were live. The nodes are offline, and the credit, co-authorship and disclosure-window terms below are not on offer now. Current reporting: SECURITY.md (best-effort). The claim itself still stands — test it on your own instance.

Elyon-Sol is a gate that refuses any action that does not carry a valid permission to act. The challenge asked security researchers to make it act on something it should not — a confirmed break would have been credited, named, and written permanently into the project's public record.

The claim to disprove. Without the gate's signing key, there is no request you can craft that (a) makes the target perform an action, or (b) makes the sidecar answer ALLOW, unless the token in the X-Elyon-Sol-Envelope header is validly signed, currently valid, bound to exactly that action and target, and not previously used. Using a real token once, as intended, is not a break — that is it working.
Why trust this. We won't oversell it — that's the point. It hasn't been externally validated, and we say so: every test to date is ours, and internal evidence is not validation. The tool adjudicates, not the author — a read-only inspector reads your token the way the target does and rules on whether you broke it. The claim is one falsifiable line, and we publish the boundaries we do not defend so we can't move the goalposts. It's all on the public record: formally specified, open source (AGPL), a citable DOI, and a ledger that logs our own corrections.

What counts as a break

  • Target break — get the target node to act (its GET /received count increments) on a request whose token is absent, forged, expired, replayed, altered, or bound to a different action/target.
  • Sidecar break — get the ext-authz sidecar to return 200 / ALLOW for a request that is not a currently-valid, correctly-bound, single-use, validly-signed token.
  • Run both against your own instance — deploy/SPIN_UP_YOUR_OWN.md stands the four services up in a couple of commands.
  • Reproducible from your steps — one reproduction beats any description.

Out of scope (please don't spend time here)

  • Denial of service, flooding, availability — refusing is the design, not a break.
  • Stealing the signing key, or compromising host OS / cloud / TLS by means outside the request protocol (welcome as separate, credited infra reports).
  • Acting on a genuinely valid, unused token — that is correct behavior.
  • "An authorized action could be unwise" — the gate checks authorization, not wisdom.

The cryptographic core held: every forged, tampered, replayed, rebound, or cross-target token was refused. The findings were in the surrounding contract and deployment wiring — where implementation seams live — and every high-severity one was fixed and deployed across all four public nodes while they ran.

This is internal, author-side work — not external validation. We publish our own findings because the entire premise is that you can trust what we claim. Finding these ourselves strengthens the surface; it does not replace an external break. External validation (G5) remains the unmet finish line.

Since that pass — gate-key revocation moved in-band

Signed key-record trust is now wired into the enforce path and was enabled on the former live target and sidecar. Revoking a gate key was previously an out-of-band re-pin of every consumer; it is now a revoked flip in a single publisher-signed record, verified per request against an out-of-band-pinned root. A revoked, expired, stale, invalid, or serial-rolled-back record fails closed — never a silent downgrade to the static pin. Exercised live over real transport: honored via the record, six of six tampering attacks refused, a revocation drill returning REF_VERIFY_KEY_REVOKED, then restore at a higher serial.

Honest note: this is author-side white-box live-ops, not an external result. It also adds an availability dependency — key-record freshness is now on the critical path, so a publisher outage or a stalled sync fails the surface closed (REF_VERIFY_KEY_RECORD_STALE) rather than open. A freshness monitor covers it.
